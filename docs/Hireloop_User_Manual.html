01 · PRODUCT

Hireloop at a glance

One web application connects people searching for work with organizations publishing openings.

Hireloop is a hiring marketplace with three account roles: seeker, recruiter, and administrator. Public visitors can explore job listings and approved company profiles. Registered seekers can apply to jobs, review recorded applications, and view their saved plan. Recruiters can create a company profile and, after approval, publish jobs subject to an active-post limit.

The product combines a public website, role-specific dashboards, MongoDB-backed records, email-and-password authentication, and Stripe-hosted subscription checkout. The frontend is a Next.js App Router application. A separate Express service exposes JSON endpoints for jobs, applications, companies, plans, subscriptions, and user data.

Job seeker

Discover roles, submit application details, see application records, and review plan information.

Recruiter

Maintain an employer profile, wait for approval, publish active openings, and stay within the plan limit.

Administrator

Review platform records, inspect applications, and approve or update company status.

Visitor

Browse public openings, explore approved companies, and inspect plans.
Current scope: The code does not show a recruiter-facing application inbox or candidate-status update workflow. The admin jobs view can inspect application records.
02 · PRODUCT

People and account roles

Choose the account that matches the work you intend to do.

Job seeker

Signup offers “Job Seeker” and “Recruiter.” The default role is seeker, with an initial seeker_free plan. The seeker area provides a home dashboard, job browsing, application history, settings, and billing screens.

Recruiter

Recruiter signup assigns recruiter_free. Recruiters create a company profile and can post only when that profile has an approved status. Active job posts consume the limit associated with the recruiter’s plan.

Administrator

The client contains an admin dashboard for users, jobs, companies, payments, and settings. Admin accounts are not created through the public signup role selector; an authorized project operator must provision the role through a trusted administrative process.

Account safety: Never ask a user to share a password or session token. The repositories do not define a public admin onboarding procedure. Keep role assignment restricted to trusted operators.

Each role is routed to a separate dashboard layout. A role mismatch can lead to an unauthorized page; sign in with the account that matches the intended task.

03 · SYSTEM

System architecture

The browser UI, Next.js server code, Express API, and MongoDB have distinct responsibilities.

Browser → Next.js pages and interactive React components → server actions / server-side data helpers → Express JSON API → MongoDB collections

Better Auth handles email/password identity and persists auth data through its MongoDB adapter. The Next.js server reads the current session and forwards its token as a bearer credential for protected API calls. The Express API checks the bearer token against its session collection and loads the matching user for protected routes.

Stripe Checkout is initiated by a Next.js Route Handler. Stripe hosts the payment page and returns the browser to the configured success route. The success page retrieves the Checkout Session and records a subscription through the Express API.

Repositories

  • hireloop-client: Next.js 16 application, React UI, Better Auth integration, Stripe calls, and server-side API helpers.
  • hireloop-server: Express 5 application, MongoDB driver, CORS and JSON middleware, API routes, and Vercel entry configuration.
Configuration must agree: The client’s NEXT_PUBLIC_BASE_URL must point to the deployed or local API origin. Authentication and API server database settings must reference the intended MongoDB environment.
04 · SYSTEM

Technology stack

Libraries and runtime choices visible in the package manifests.

  • Next.js 16.4.2 and React 19.3: App Router pages, layouts, server components, server actions, and a Route Handler.
  • HeroUI, Tailwind CSS 4, Lucide, Gravity UI icons, and Motion: interface components, styling, iconography, and animation.
  • Better Auth 1.7.11 and MongoDB adapter: email/password identity and session persistence.
  • MongoDB Node driver 7.7: application data operations in the Express server and auth setup.
  • Express 5.3 and CORS: JSON API and cross-origin request handling.
  • Stripe 23 and Stripe.js: subscription checkout integration.
  • Vercel Node deployment configuration: server entry routing in vercel.json.

Version ranges are declared in package manifests, so the lockfiles determine the resolved versions installed for a build. The client uses npm scripts for development, build, start, and ESLint. The server exposes start and nodemon development scripts; its test script intentionally exits with “no test specified.”

Framework guidance: The client repository contains version-specific Next.js agent instructions. Read the installed documentation under node_modules/next/dist/docs/ before changing routing or framework behavior.
05 · DATA

Data model overview

MongoDB collections used by the application API.

  • user: Better Auth user records plus Hireloop role and plan fields.
  • session: sessions that the API uses to validate bearer tokens.
  • jobs: job data, company identifiers, status, posting metadata, and creation date.
  • companies: recruiter association, company profile values, status, and creation date.
  • applications: application payload, applicant/job references, optional links/status, and creation date.
  • plans: plan definitions, display information, and quota configuration such as maximum active posts.
  • subscriptions: purchase metadata and creation date.

Jobs associate to companies through string companyId. Recruiter company lookup uses recruiterId. Subscription completion updates a user’s plan by email. ObjectId validation is applied to job-detail and company-update identifiers.

Schema discipline: The API uses flexible JSON documents rather than a schema-validation layer. Keep field names and identifier formats consistent between UI forms, stored documents, and admin views. Define indexes, retention rules, and backup procedures for a production deployment.

Collection names are declared in hireloop-server/index.js; auth database selection is configured separately in the client’s auth module.

06 · GETTING STARTED

Public website navigation

Visitors can explore the platform before creating an account.

The landing page introduces Hireloop and includes job listings, product features, statistics, and plan previews. The top navigation links to the job directory, company directory, and plans. A signed-in user sees a role-specific dashboard link and an account/sign-out control.

Browse jobs

Open /jobs to see open positions. Select a card to view its job details. The job directory is also linked from the landing page and dashboard.

Browse employers

Open /companies to see companies whose status is “Approved” (case-insensitive). A company card may show its logo, industry, location, employee count, description, and website.

Compare plans

Open /plans to switch between seeker and recruiter plan groups, review displayed pricing and feature summaries, and proceed to checkout for a paid plan.

Helpful habit: Use the site navigation rather than guessing URLs. If a dashboard page redirects or shows “unauthorized,” check that you are signed in and that your role matches that workspace.
07 · SEEKERS

Create a job-seeker account

Signup creates a personal Hireloop account and a default plan.

  1. Open /auth/signup or choose the signup action from the sign-in page.
  2. Enter your name and email address.
  3. Choose a password with at least six characters.
  4. Select Job Seeker as the account role.
  5. Submit the form and wait for the account-created confirmation and redirect.

The form assigns the seeker role and seeker_free plan. It reports validation errors for a blank name, blank email, or password shorter than six characters. Better Auth handles the account creation request and returns any authentication error for display.

Use a unique email address and a password you do not reuse. The project does not document a password-reset or email-verification flow; do not assume those flows are available.

If signup reports a network error, confirm the client is running, auth/database configuration is valid, and the browser can reach the configured auth endpoint. If an account already exists, use the sign-in screen.

Recruiters should choose the recruiter role at signup. Changing roles is not offered as a normal profile setting.

08 · ACCESS

Sign in and sign out

Use the same email address and password used when registering.

Sign in

  1. Open /auth/signin.
  2. Enter your email address and password.
  3. Submit and wait for confirmation.
  4. After the redirect, open the dashboard or return to the page you originally requested.

The sign-in form displays auth errors inline and prevents repeated submissions while a request is in progress. The password visibility control can reveal or conceal the value while entering it.

Sign out

Use the account menu’s sign-out action in the navigation bar. Better Auth clears the local authenticated session; afterward, protected dashboard access should require a fresh sign-in.

Session troubleshooting: If a protected action returns unauthorized, sign out, sign in again, and retry. Confirm the browser is not blocking the application’s session cookies and the API URL is correct.

The account menu directs seekers, recruiters, and admins to their corresponding dashboard roots. A valid session does not grant every role’s permissions; both the page and API may enforce role checks.

09 · ACCESS

Role-based navigation

Hireloop uses the account role to choose a dashboard and protect some operations.

Seeker

/dashboard/seeker
Dashboard, jobs, applications, settings, billing.

Recruiter

/dashboard/recruiter
Dashboard, job posts, company profile, settings, profile.

Administrator

/dashboard/admin
Overview, users, jobs, companies, payments, settings.

Unauthenticated

/auth/signin
Sign in to access account workspaces.

Dashboard layouts call a role guard. The session helper redirects a missing session to sign-in and a mismatched role to /unauthorized. On protected Express endpoints, bearer-token validation loads the user, then route middleware checks for seeker, recruiter, or admin role.

Role is a permission boundary. Do not use a role selector or client-side state as proof of authorization. The server must check identity and role before sensitive reads or changes.

If the wrong workspace opens, verify the active account’s role in settings (where shown) and sign out before switching accounts.

10 · SEEKERS

Seeker dashboard

A starting point for searching and reviewing your account activity.

Open /dashboard/seeker after signing in as a seeker. The dashboard layout provides role-specific navigation. Use the job link to search openings, the applications link to review submitted records, the settings page for an account snapshot, and billing for plan details and subscription history.

Suggested first session

  1. Confirm the displayed account name, email, and role.
  2. Open Browse Jobs and apply filters that match your interests.
  3. Read a full job description before choosing Apply.
  4. Return to Applications to check that your record appears.
  5. Review the plan and its displayed features in Settings or Billing.
Application status: The application table displays the status saved on the record; missing status values may be presented as “Applied.” The current server code does not provide a seeker endpoint to change an application’s status.

Use the same account when returning. Subscription and application records are associated with the signed-in identity, so a second account will not show the first account’s data.

11 · SEEKERS

Browse and filter jobs

Search the public or seeker job directory, then narrow results using the available controls.

  1. Open /jobs or /dashboard/seeker/jobs.
  2. Review job cards for title, company, category, type, and location/work arrangement.
  3. Use the filter controls to narrow the loaded results.
  4. Open a promising listing to read its full details.

The server fetches jobs from the Express GET /api/jobs endpoint. The listing container receives initial job data and handles interactive filtering in the client. Job status can be queried by API; the page’s exact filtering options are those rendered in the current filter component.

Search tip: Try one filter at a time. A result set with no matches may mean the selected category, location, or work mode is too narrow; clear filters and broaden the search.

Remote positions show a Remote label. Non-remote postings use their location field. A job may no longer be active after the page loads, so review the details and deadline before preparing an application.

No saved-job persistence workflow is evident in the seeker screens, despite plan-card copy that mentions saving jobs.

12 · SEEKERS

Read a job listing

Check the role requirements and terms before sharing application details.

Open a job card to visit its detail route, /jobs/[id]. A full listing can include the job title, company, job category, job type, location or remote status, salary range and currency, application deadline, responsibilities, requirements, benefits, and status.

Before applying

  • Confirm the employer and role are relevant to your search.
  • Check whether the position is remote or tied to a location.
  • Review the job type and compensation fields when provided.
  • Read responsibilities, requirements, and benefits carefully.
  • Check the deadline and prepare accurate resume/portfolio links.

Select the apply action to open the application form for that job. If a job cannot be loaded, return to the directory and try another listing; malformed identifiers are rejected by the API.

Be thoughtful with personal data. Application links and any text entered are sent to the platform API and stored with an application record. Share only the information requested and use links you are comfortable sharing with the employer.
13 · SEEKERS

Submit an application

The application form records your details against a selected job.

  1. Open the job’s application route, typically /jobs/[id]/apply.
  2. Enter the requested applicant details and optional professional links.
  3. Review the job and contact information for accuracy.
  4. Submit once and wait for the result before retrying.
  5. Open the Applications page to confirm the new record appears.

The client submits application data through a server action. The Express API stores the submitted JSON plus a creation timestamp. The admin jobs view recognizes optional resumeLink and portfolioLink values. Keep all links publicly accessible to the intended reviewer, or use a sharing configuration that grants access.

Current implementation detail: The Express POST /api/applications route does not apply token or seeker-role middleware. The user interface is designed for seekers, but server-side authorization and duplicate-application protections should be added before production use.

If submission fails, verify the required fields, network connection, and configured API URL. Do not submit repeatedly until you have checked whether a record was already created.

14 · SEEKERS

Track applications

Review application records associated with your signed-in account.

Open /dashboard/seeker/applications. The page reads the current user session and requests applications filtered by that user’s identifier. The Express route requires seeker authorization and rejects an applicant identifier that does not match the authenticated user.

The table receives application data and can show job-related information, submitted date, and a status value. In the admin jobs page, application rows can also expose the applicant, submission time, status, resume link, and portfolio link.

If an application is missing

  • Check that you are signed into the same account used to apply.
  • Refresh the page after the submission has completed.
  • Check the submitted job’s application route and connectivity.
  • Contact the project operator if the record still does not appear.
Workflow boundary: Recruiters currently lack a dedicated candidate/application review screen in their dashboard routes. Admins can inspect applications through the job review screen; a recruiter pipeline is a product extension.
15 · SEEKERS

Seeker account settings

Review account identity, email state, current plan, and shortcuts.

Open /dashboard/seeker/settings. The screen displays your name, email, account role, membership month when available, email verification state, and current plan details. Links lead to application history, job browsing, billing, and the seeker dashboard.

The settings page is primarily an account snapshot. The UI explicitly notes that profile editing, notification preferences, and password controls are not currently available from seeker settings. Use the auth screens for sign-in; no recovery route is documented in the project.

Plan mismatch or missing data? The screen loads plan details from the API and falls back to a readable version of the saved plan identifier when details are unavailable.

To keep your records consistent, use one account email for job applications and plan purchases. Ask an administrator through the project’s agreed support channel if your identity details need to be corrected.

17 · SEEKERS

Billing and subscription history

Review the plan saved on your account and recorded subscription entries.

Open /dashboard/seeker/billing or use the Billing link in Settings. The page shows the current plan name, price/period and features when available, then lists matching subscription records newest first.

The billing screen loads the subscription collection and filters records by user identifier or normalized email on the server-rendered page. The latest record is tagged. This history represents records written by the application and should not be treated as a complete invoice ledger.

Change plan

Choose Change Plan to open /plans, choose a paid seeker option, and continue to hosted Stripe Checkout. The app saves the resulting plan to the user after the success page verifies a completed Checkout Session.

Not currently provided here: A self-service cancellation action, payment-method management portal, downloadable invoice list, refund workflow, or subscription renewal status synchronization is not evidenced in the client code.
18 · RECRUITERS

Recruiter onboarding

Create a recruiter account, establish your company profile, and wait for review.

  1. Sign up and select the Recruiter role.
  2. Open the recruiter dashboard and go to Company Profile.
  3. Enter accurate employer details and submit the profile.
  4. Wait while an administrator reviews company status.
  5. After approval, create job posts within your current plan limit.

Recruiter signup defaults to recruiter_free. Recruiter profile pages display the associated company and saved plan. A recruiter is associated with a company through its recruiterId value.

Approval gate: The posting form is available only when company status is exactly Approved. A newly created, missing, or differently cased status may prevent posting. Ask the administrator to review the company record rather than repeatedly submitting job posts.

Ensure the company name and website are accurate: the approved profile may be visible in the public company directory.

19 · RECRUITERS

Company profile setup

Create a clear employer profile before publishing vacancies.

Open /dashboard/recruiter/company. The page loads the company associated with your recruiter account and renders the company profile editor. The profile view supports company information such as name, description, website URL, logo, industry, location, and employee count.

Good profile practice

  • Use the organization’s public name and a working official website.
  • Describe the business and the kinds of roles it hires for.
  • Provide consistent location, industry, and company-size values.
  • Use a logo that your organization has permission to publish.
  • Review values before submitting for administrator approval.

The server stores company records in MongoDB and stamps new records with createdAt. The public directory includes only approved profiles. Recruiter company lookup reads by recruiter identifier.

Profile missing? Confirm the current account is a recruiter and refresh after submission. If the account has no associated company record, the recruiter cannot pass the job-post quota lookup.
20 · RECRUITERS

Company approval workflow

Company status controls public visibility and recruiter job-post access.

An administrator reviews company information in the admin company workspace and updates the company’s status. The API exposes a protected PATCH /api/companies/:id endpoint for an admin to set the status. The public company directory filters for the value “Approved,” ignoring case.

The recruiter posting form checks for company.status === 'Approved' before rendering the form. Use the exact “Approved” status to satisfy this UI gate. If the company is pending or not approved, the interface indicates that approval is needed.

Operational check: Confirm that the profile is linked to the recruiter’s account and has the intended status. Approval is a workflow state; it does not verify the organization’s legal identity automatically.

The company status update route validates the MongoDB ObjectId and requires an authenticated admin. The admin UI should be used for routine decisions; API-level controls remain the enforcement point.

21 · RECRUITERS

Recruiter dashboard

Access the recruiter workspace and the tools available in the current build.

Open /dashboard/recruiter while signed in with a recruiter account. The home page greets the user, shows personal account information, and provides shortcuts to post a job, manage the company profile, and explore plans.

Other recruiter pages include job posts, a new-job form, a company workspace, profile, and settings. The recruiter profile displays personal details, associated company information, plan details, and shortcuts to job posts.

Application review: The recruiter profile itself states that candidate application history is not currently exposed as recruiter profile data. A complete hiring workflow needs an authorized recruiter application list and candidate status actions.

For a new recruiter account, complete the company profile first. Then check approval and posting quota before preparing a new role.

22 · RECRUITERS

Prepare an effective job post

Accurate listings help candidates decide whether to apply.

The job-post form collects title, category, job type, salary range, currency, location/remote state, application deadline, responsibilities, requirements, and optional benefits. Current category choices shown in the form include technology, design, marketing, and sales. Job types include full-time, part-time, contract, and internship.

Before you begin

  • Confirm your company is approved and linked to your recruiter account.
  • Choose a concise, recognizable title and the closest category.
  • State location or switch Remote on; non-remote location is required.
  • Keep salary minimum and maximum consistent and specify currency.
  • Write specific responsibilities and realistic requirements.
  • Set a valid application deadline and review all text.
Candidate trust: Avoid misleading pay ranges, discriminatory requirements, broken links, and sensitive information in public descriptions.
23 · RECRUITERS

Publish a job

An approved recruiter can submit a validated active job post.

  1. Open /dashboard/recruiter/jobs/new.
  2. Confirm the displayed company is correct and approved.
  3. Complete the required job fields and address inline validation.
  4. Submit once and wait for completion.
  5. Return to recruiter job posts and verify the role appears.

The server accepts recruiter job creation through POST /api/recruiter/jobs (the general POST /api/jobs route is also role-protected). The handler validates the authenticated recruiter, confirms the submitted company ID matches the recruiter’s own company, enforces the active-job quota, stores company identity and creation time, and returns the inserted ID.

The client revalidates the public jobs and recruiter jobs pages when creation succeeds.

If posting is blocked: Check the company association, exact Approved status, and active-job count. A quota response includes a limit-reached indicator and plan information.
24 · RECRUITERS

Active-job quotas

Recruiter plans cap the number of active postings at one time.

Free

3 active job posts

Growth

10 active job posts

Enterprise

50 active job posts

Source of limit

Plan document configuration, with server fallback values for known recruiter plan IDs.

The quota API reports the plan ID/name, current active jobs, limit, and whether the limit has been reached. The server counts job records with the recruiter company ID and status: active. A job must be deactivated/removed by an available administrative process before its slot can be reused; the recruiter UI does not show a corresponding status-change action.

Plan activation: The subscription success flow updates the user’s plan field. Ensure the corresponding plan document or fallback ID is configured so the limit can be resolved.

Upgrade through the Plans page if you need a higher tier. Verify the account shows the intended plan after Checkout returns.

25 · RECRUITERS

Manage recruiter job posts

Review the jobs associated with your company.

Open /dashboard/recruiter/jobs to view the recruiter job table. The route loads jobs belonging to the company and presents information such as title, category, location/remote status, and status.

The interface displays action icons for viewing, editing, and deleting, but the server routes in the current index.js do not define recruiter-owned job update/delete endpoints. Treat those controls as unfinished unless the current UI provides a working handler in your deployed version.

Current scope boundary: Job creation and quota checking are implemented. A complete self-service edit, close, reopen, or delete workflow is not demonstrated by the server API.

If a role must be corrected or closed, use the project’s approved administrative process and confirm the change in the public job directory. Avoid promising candidates that a listing has been removed until its stored status and visibility are checked.

26 · DISCOVERY

Company directory

Candidates and visitors can explore approved employers.

Open /companies. The page loads company records from the API, then shows only companies whose status is approved. A company card can include the logo, name, industry, location, employee count, description, and external website link.

If the directory shows no companies, either there are no approved records yet or the company request failed. A loading/data error is reported separately from an empty directory. The external website link is normalized to HTTPS when the stored value has no scheme.

Recruiter tip: Keep the company profile current; it is the public representation candidates will see. Ensure all public claims and links are accurate.

Public visibility is distinct from posting authorization, which also depends on the recruiter’s account association, approval state, and plan quota.

27 · ADMIN

Administrator workspace

The admin dashboard provides oversight pages for key platform records.

Open /dashboard/admin with an admin account. The admin layout provides links to overview, users, jobs, companies, payments, and settings. The overview presents dashboard metrics and navigation into management screens.

Admin routes use a role guard in the dashboard layout. Server endpoints for protected admin applications and company updates also validate the session token and admin role. Read-only aggregate pages use API data to summarize accounts, jobs, applications, companies, or subscriptions.

Limit access: Admin accounts can access sensitive user and application data. Provision them only through a trusted operator, use strong unique credentials, and review access periodically.

Use admin tools for review and controlled moderation. The admin UI is not a substitute for a documented support, data-retention, or incident-response process.

28 · ADMIN

Manage users and companies

Review accounts and decide which company profiles are approved for public display.

Users

The user screen reads user records and summarizes seekers and recruiters. It displays account identity, role, plan, email verification state, and join date. The current screen is primarily an overview; it does not expose every account-edit or deletion operation.

Companies

The companies screen shows company records and provides status controls. Use status review to approve eligible recruiter profiles or keep them from public discovery. Updates are sent to the admin-only company PATCH endpoint.

Review checklist: Confirm the profile belongs to the expected recruiter, inspect company name and public links, select an explicit status, submit the update, and verify the public directory reflects the decision.

The API currently accepts a status field update. It does not establish a detailed approval audit trail with reviewer identity and rationale; maintain those records through a separately approved operational process if required.

29 · ADMIN

Review jobs and applications

The admin job screen groups application records under published roles.

Open /dashboard/admin/jobs. The page loads job records and admin application records, then presents each job with its status and associated applications. Application details can show applicant name/email, submitted time, status, and optional resume or portfolio links.

Use this view to understand platform activity and investigate missing or inappropriate content. A link may open an external resource in a new tab; confirm the destination before relying on it.

Privacy: Applicant details and career documents are sensitive personal data. Access them only for a legitimate operational reason and do not copy/share them outside authorized channels.

The admin applications API is protected by admin role middleware. The recruiter interface does not currently expose a dedicated, company-scoped application pipeline or candidate status-update endpoint. Building that workflow requires server-side ownership checks, explicit allowed status transitions, and a recruiter UI.

30 · PLANS

Plans and monetization

The UI offers separate seeker and recruiter plan tiers.

Seeker

Free $0; Pro $19/month; Premium $39/month.

Recruiter

Free $0; Growth $49/month; Enterprise $149/month.

Paid plan IDs are seeker_pro, seeker_premium, recruiter_growth, and recruiter_enterprise. The Stripe module maps these IDs to configured Price IDs. Free plans are not listed in that paid-price map.

The plan catalog endpoint reads plan data from MongoDB. Recruiter active-post limits are resolved from plan fields where configured, with server defaults of 3, 10, and 50 for the known recruiter tiers.

Keep prices aligned: Plan UI prices, Stripe Price IDs, MongoDB plan documents, and admin payment summaries are maintained in separate code/data locations. Review all four when changing prices or features. Current admin payment totals use fixed displayed prices, not Stripe settlement records.
31 · PAYMENTS

Stripe checkout lifecycle

Checkout is hosted by Stripe; Hireloop records a subscription after a completed session.

  1. Choose a paid plan in the plan UI.
  2. The client posts plan_id to /api/checkout_sessions.
  3. The Next.js route maps the plan to a Stripe Price ID and creates a subscription-mode Checkout Session.
  4. Stripe redirects to its hosted payment page, then returns to the Hireloop success URL.
  5. The success page retrieves the session and, when complete, sends subscription metadata to the API.
  6. The API inserts a subscription record and updates the user plan by email.

The checkout session metadata contains the plan ID. The application does not show a Stripe webhook handler in the source tree. Successful plan persistence therefore depends on the user returning to the success page.

Production readiness: Use verified webhooks for reliable subscription lifecycle updates, validate server-side user/plan mapping, and provide cancellation/payment management. Never expose the Stripe secret key in browser code.
32 · END TO END

End-to-end seeker journey

A typical path from first visit to a recorded application.

Visit site → Browse jobs → Sign up / sign in → Open job detail → Submit application → Review Applications → Check account plan
  1. Open the public job directory and filter for a suitable role.
  2. Read the job description, requirements, location, and deadline.
  3. Sign in or create a seeker account when ready to apply.
  4. Complete the application form and submit once.
  5. Check the application history page for the new record.
  6. Use Settings and Billing to review saved account/plan information.

The application is stored as a MongoDB document with a creation date. The seeker API reads only records matching the authenticated applicant ID.

Expected limitation: There is no documented notification or recruiter response mechanism in the current client. Application status may remain at its initial saved value until an authorized process changes the record.

Keep a copy of the job title and submission date for your own reference.

33 · END TO END

End-to-end recruiter journey

A typical path from recruiter signup to a published opening.

Recruiter signup → Company profile → Admin review → Plan/quota check → Create job → Public listing
  1. Register with the recruiter role and sign in.
  2. Create a complete company profile.
  3. Wait for an admin to set the company status to Approved.
  4. Review current plan and available active-post slots.
  5. Prepare a complete job post and publish it.
  6. Verify the listing in public search and the recruiter job table.

The server binds the post to the recruiter’s own company and enforces its active-job count. Job creation fails if no recruiter company exists, the submitted company ID differs, the plan has no resolvable limit, or the quota is full.

Application handling is incomplete: A recruiter cannot currently review and progress candidates through a dedicated recruiter pipeline in the provided routes. Plan an authorized human process until that capability is built.
34 · END TO END

End-to-end admin journey

A controlled review cycle for company approval and platform oversight.

  1. Sign in using an admin-provisioned account.
  2. Open Companies and review new recruiter profiles.
  3. Set an explicit status and verify the update.
  4. Confirm approved organizations appear in the public directory.
  5. Review jobs and applications when investigating platform activity.
  6. Use Users and Payments pages for high-level operational review.

Company approval affects company-directory visibility and recruiter job-post access. Admin job review groups application records with roles. The payments page derives summaries from saved subscription rows and fixed plan prices.

Audit discipline: Record approval decisions and sensitive-data access using the project’s authorized process. The current data model does not show a complete moderator audit log or payment transaction ledger.

When an issue cannot be resolved through the available UI, capture the relevant record identifier and reproduce the issue in a safe environment before changing data manually.

The remaining Express API surface and its current access behavior.

  • GET /api/applications — authenticated seeker list; enforces applicant-ID ownership.
  • POST /api/applications — inserts submitted application with creation date; currently lacks auth middleware.

38 · SECURITY

Authentication and authorization

Better Auth sessions connect the Next.js identity to selected API permissions.

The client initializes Better Auth with MongoDB persistence and email/password enabled. User additional fields include a role defaulting to seeker and plan defaulting to seeker_free. Server-side session helpers read the current request headers and return the session user or token.

API helpers attach the session token as a bearer header. Express looks up that token in the session collection, finds the user by session user ID, and assigns the user to the request. Role middleware protects recruiter job creation, seeker application reads, admin application reads, and company status updates.

Implementation review findings: The Express API exposes several user/company/application/subscription operations without authentication. Subscription creation updates a user by caller-supplied email. The checkout route should reject unauthenticated users and unknown plan IDs before calling Stripe. These are code-review findings to resolve before production.

Use HTTPS, secret environment variables, secure session/cookie settings, request validation, least-privilege database credentials, and a webhook signature check for payment events.

Environment and configuration

Set environment-specific values locally and in the deployment platform.

Client

NEXT_PUBLIC_BASE_URL — Express API origin.

40 · OPERATIONS

Local development setup

Run the client and API as two separate processes.

  1. Install a supported Node.js runtime and npm.
  2. Install dependencies in each repository with npm install (or npm ci from lockfiles).
  3. Set the client and server environment values described on page 41.
  4. Start the Express API from hireloop-server with npm run dev; default port is 5000.
  5. Point client NEXT_PUBLIC_BASE_URL at that API origin.
  6. Start the Next.js client from hireloop-client with npm run dev; open the local development URL printed in the terminal.

Client scripts also include npm run build, npm start, and npm run lint. The server uses npm start for its production entry and npm run dev for nodemon.

Database compatibility: Better Auth and Express must agree on where their relevant user/session records live for bearer-token verification to succeed. Check the configured databases and session token storage before troubleshooting the UI.
41 · OPERATIONS

Deployment overview

Deploy the web application and API with matching settings and secure secrets.

The server repository includes a Vercel configuration that builds index.js using @vercel/node and routes requests to the Express app. The server listens on a local port only when VERCEL is not set, then exports the app for the platform runtime.

The client package supports a production build and Next.js start command. Deploy it to a Next.js-compatible host, configure the API base URL to the deployed Express origin, and set auth/Stripe variables in the host’s secret environment configuration.

Release sequence

  1. Provision MongoDB database access and indexes/backups.
  2. Configure and deploy the API; verify its root responds.
  3. Configure and deploy the client using the correct API/auth URLs.
  4. Set Stripe test/live keys and paid Price IDs for the target environment.
  5. Run a complete seeker, recruiter, admin, and payment flow in staging.
  6. Review logs, CORS origins, HTTPS, secrets, and access controls.
Before launch: Resolve the authorization gaps and webhook/lifecycle gaps on pages 40 and 33. A successful deployment is not evidence that the workflows are production-safe.
42 · OPERATIONS

Data operations and maintenance

Reliable hiring software needs routine backup, monitoring, and record hygiene.

  • Back up MongoDB on a schedule and test restoration in a separate environment.
  • Monitor API and client errors without logging passwords, tokens, or full applicant documents.
  • Review database indexes for session-token lookup, job/company queries, and user-email updates.
  • Document record retention and deletion rules for applications and subscriptions.
  • Reconcile paid plans with Stripe’s authoritative subscription state.
  • Track company status decisions and administrative changes.

The application currently stamps jobs, companies, applications, and subscriptions with a creation date. It does not show a comprehensive migration framework, retention job, audit log, or payment reconciliation task.

Safe data changes: Prefer an authenticated admin operation or reviewed migration over ad hoc database edits. Record the reason, backup first, and verify the affected user-facing pages after the change.

Set alerts for repeated 500 responses, MongoDB connectivity failures, Stripe API errors, and unexpected growth in sensitive collections.

43 · QUALITY

Privacy, security, and limitations

Protect applicant data and treat this repository as an evolving project.

Data handling

Applications may contain identity details and resume/portfolio URLs. Restrict who can read them, use HTTPS, avoid unnecessary copies, define a retention schedule, and make privacy practices visible to users.

Code-level concerns to address

  • Protect public user and subscription list endpoints with admin authorization.
  • Authorize application creation and bind it to the authenticated seeker.
  • Authorize company creation/lookup and validate recruiter ownership.
  • Validate subscription plan IDs and derive the target user from the active session.
  • Add request schemas, rate limits, and secure production CORS settings.
  • Use Stripe webhooks and verify event signatures for subscription lifecycle updates.
Known product gaps: No recruiter application pipeline, password reset flow, visible profile editing workflow, saved-job persistence implementation, or complete subscription self-service is evidenced in the inspected code.

This is an implementation review, not a penetration test or legal compliance assessment. Complete a security review before processing real applicant or payment data.

45 · SUPPORT

Troubleshooting guide

Check the simplest causes first and capture enough detail to reproduce the issue.

  • Cannot sign in: Verify email/password, confirm the auth URL/database configuration, and retry after signing out.
  • Dashboard says unauthorized: Check account role and session; sign in to the matching role.
  • Jobs fail to load: Confirm the API is running and NEXT_PUBLIC_BASE_URL points to it.
  • Recruiter cannot post: Check company association, exact Approved status, plan, and active-post count.
  • Company is not public: Verify status is Approved and reload the directory.
  • Application not visible: Confirm same seeker account, successful submission, and applicant ID association.
  • Plan not updated: Confirm Checkout completed and success page returned; inspect server/API logs and saved user plan.
  • Checkout fails: Verify Stripe key, Price ID mapping, plan ID, and request origin.
When escalating: Provide the route, role, time, error text, and steps to reproduce. Never include passwords, secret keys, or bearer tokens.

Glossary and support

Shared vocabulary for users and maintainers.

  • Applicant / seeker: a person searching for a role and submitting an application.
  • Recruiter: an employer-side account that manages a company profile and publishes openings.
  • Company status: moderation state used for company directory visibility and posting access.
  • Active job: a job record with status active; it consumes a recruiter plan slot.
  • Plan ID: a stable identifier such as recruiter_growth stored on a user or subscription.
  • Bearer token: session token sent in an API Authorization header for protected requests.
  • Checkout Session: Stripe-hosted payment session created for a selected paid plan.
  • API: Express routes that read/write Hireloop records in MongoDB.

No dedicated support email or service desk is defined in the repository. Project owners should publish a support contact, response expectations, privacy notice, and escalation path before inviting external users.

For project handover: Include repository URLs, deployment owners, environment variable inventory (without secret values), database ownership, Stripe account ownership, and a recovery contact.
